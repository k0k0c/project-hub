# Тексты и локализация Project Hub

Пишите для человека, который пользуется Codex и следит за задачами, но может
не знать внутреннюю архитектуру Hub. Это проектный редакционный skill;
он не меняет поведение инструментов и не означает наличие перевода интерфейса.

## Справка для новых пользователей

Справка и встроенные тексты поставляются всем пользователям Project Hub.
Не переносите в них контекст текущей разработки: названия подключённых проектов,
имена разработчиков, локальные пути и сведения о параллельной работе.
Описывайте действия и устройство Hub так, чтобы текст был понятен при первой
установке. Если пример необходим, используйте нейтральный вымышленный пример
и явно обозначайте его как пример. Название реально выбранного проекта допустимо
в данных интерфейса, но не в общем справочном тексте.

## Единое обращение

В русском интерфейсе используйте «вы», «ваш», «ваши» со строчной буквы.
Сохраняйте этот тон во всём разделе, включая формы, подсказки, пустые состояния,
подтверждения, ошибки и справку, адресованные пользователю.
Не переключайтесь на «ты» и единственное число повелительного наклонения.
Например: «когда работаете», «применяйте», «выберите», «сохраните».
При переводе выбирайте естественный для языка тон, сохраняя смысл и уважительное
обращение, без буквального переноса русской грамматики.

Отдельно определяйте адресата цитируемого текста. Инструкция для агента может
использовать «применяй», «найди», «сообщи»: это не смена обращения к пользователю.
Не преобразуйте её на «вы» только потому, что она показана внутри интерфейса.
Обозначайте назначение блока, сохраняйте оригинал, смысл требований и имена API.
Правило единого обращения действует на пояснения вокруг инструкции. Аналогично
различайте пользовательскую форму, шаблон инструкции агенту и точный контракт API.

## От общего к деталям

Начинайте каждую тему с назначения, области действия и главного выбора
пользователя. Затем объясняйте действия и их последствия; технические подробности
раскрывайте по желанию. Уточняйте, что именно можно редактировать, где это действует,
что заменит восстановление и когда изменения прочитает агент.

Объясняйте незнакомые термины при первом появлении. Например, вместо «значение
из комплекта» пишите «начальный шаблон из установленной версии плагина».
Не смешивайте русский и английский в обычной фразе. Точные имена MCP-инструментов,
файлов и событий сохраняйте там, где они нужны для настройки или диагностики.
Не выводите служебные ID без практической пользы.

Не повторяйте один длинный текст как действующую инструкцию, оригинал и шаблон.
Показывайте альтернативу для восстановления, когда она отличается, и объясняйте
её назначение. Заголовки страницы должны оставаться выше заголовков цитируемой
инструкции и по смыслу, и по размеру, и в структуре HTML.

## Проверка и будущие переводы

Перед передачей результата прочитайте весь затронутый раздел, а не только новую
фразу: проверьте единое обращение, термины, заголовки и повторяющиеся пояснения.
Особенно проверяйте содержимое, полученное из шаблонов и локальных пользовательских
файлов: оно может отличаться от исходников интерфейса. Пользовательские изменения
сохраняйте; исправляйте только согласованные фразы.

Используйте полные естественные формулировки, пригодные для перевода. Сохраняйте
одинаковое значение терминов и отделяйте объяснение для человека от исходного
контракта для агента. Не обещайте выбор языка, пока он не реализован. Проверки
выбирайте по проектному skill project-hub-testing; редакционная правка сама по
себе не требует полного набора тестов.
