# Документация и архитектура Project Hub

Разделы работают с выбранным проектом. Язык, аудитории, компоненты и названия
приложений задаются его настройками; в общем UI/API нет схемы конкретного продукта.

## Начало работы

Откройте «Архитектура и код» → «Инструменты» → «Настройки знаний» →
«Редактировать правила анализа». Задайте `components` с `id`, `title`
и относительными префиксами `paths`, а также основные файлы `entrypoints`.
Необязательный `parent` связывает компонент с родительской подсистемой.
Идентификаторы уникальны, родитель должен существовать, циклы запрещены.
Без явного списка точки входа обнаруживаются по синтаксису. Каталоги тестов
можно исключить через `excludeDirectories`. Компоненты с пересекающимися
префиксами сопоставляются по самому длинному совпадению; при одинаковом префиксе
побеждает вложенный компонент, а для несвязанных компонентов — порядок настройки.
Так можно отдельно описать приложения, их UI, модель, общие форматы и тестирование.
Дополнительные зарегистрированные корни адресуются через `@roots/1/`, `@roots/2/`
и так далее; `context.rootRefs` возвращает актуальные префиксы.
Если к проекту подключены дополнительные рабочие корни, `scanRoots=["0"]`
ограничивает анализ основным репозиторием; пустой список охватывает все
зарегистрированные корни. Это настройка проекта, без изменения каталога Codex.

«Сканировать» запускает локальную фоновую задачу. Она не импортирует Python-модули,
не собирает Java-проект, не запускает приложение и не обращается к ИИ.
Python использует стандартный AST, Java — parser локального JDK (Java 17+).
Другие языки пока получают инвентаризацию файлов с явно указанной capability.
Нет каталога методов, параметров и переменных. Внутренние ссылки синтаксические:
они не гарантируют динамический dispatch или полный порядок исполнения.
Неоднозначные типы показываются как неразрешённые зависимости.

Исследовательский навигатор содержит «Архитектуру», «Исходники» и «Карты».
Подсистема открывает один следующий уровень; собственный код раскрывается
отдельным действием. Локальные запросы дают сохраняемые фрагменты с проверкой
актуальности исходников; пользователь явно добавляет результат на холст.
Файлы опциональны. A/B и владельцы веток позволяют исследовать связи и сворачивать
результаты без удаления общих элементов. Подробности в
[описании рабочего пространства](../architecture-workspace.md) и
[настройке провайдеров](language-providers.md).

Один щелчок выбирает объект, двойной щелчок или «Открыть выбранное» открывает
его окружение. Переключатель слежения рядом со сворачиванием навигатора
раскрывает и минимально прокручивает точную строку в исходниках и «На схеме».
Выбор не меняет клавиатурный фокус, камеру или историю. Назад/Вперёд восстанавливают
область и её камеру. Новый раздел показывается после атомарной загрузки одной версии.

Новый раздел и каждое явное раскрытие получают одну компоновку ELK. После
раскрытия сохраняются масштаб и экранная точка выбранного узла; автоматические
перестроения отключаются. Команда «Автокомпоновка» повторяет расчёт явно.
«Вписать всё» и «Фокус»/F управляют камерой отдельно. Позиции и маршруты
сохраняются по модели и версии политики; несовместимые старые кэши отбрасываются.

Форма линий фиксирована: обычные зависимости — Round taxi по ортогональным
маршрутам ELK; предок–потомок и петли — компактные кубические SVG-маршруты
с предсказуемыми портами. Пользовательского выбора Bezier/Taxi/segments нет.
Дублирующие вложенность contains-линии скрыты рамками, но сохраняются в фактах.
Перенос или изменение размера карточки пересчитывает её порты по фактическим
границам. Колесо использует плавную адаптивную скорость и сохраняет точку под
курсором; чувствительность нормализуется по deltaMode без notch-порогов.

«Перечитать данные» и «Сканировать исходники» разделены. Статус задания,
очередь, завершение, ограничения и ошибки видны в навигаторе; повторный запуск
во время работы не добавляет задание. Опрос статуса не пересоздаёт карту.
Подробное руководство: [Навигатор архитектуры](../architecture-workspace.md).

Цвет карточки обозначает тип, цвет связи — семантику, штрих — происхождение факта.
Использование и зависимость показаны синим, импорт — розовым с точечным
штрихом, наследование — зелёным с пустой стрелкой, включение — фиолетовым.
На плотных схемах подписи раскрываются при выборе или наведении на связь;
инспектор показывает её описание, направление и исходные строки. Это сохраняет
читаемость узлов с большим количеством входящих и исходящих связей.

«Карта компонентов» показывает дочерние подсистемы одного уровня. Переход внутрь
компонента открывает следующий уровень. «Матрица» сравнивает те же компоненты:
строка — источник зависимости, столбец — получатель. Числа означают количество
различных статических связей, агрегированных из исходников; это не счётчик вызовов.
Зависимости вложенных подсистем сворачиваются до их родительских компонентов.
Неполная выборка отмечается явно; отсутствие загруженной связи не выдаётся за
доказанное отсутствие зависимости. Выбор ячейки открывает соответствующее окружение.

Граф рисует локально поставляемый Cytoscape.js 3.33.1 (MIT), без CDN. Навигация
по символам опирается на [Sourcetrail](https://github.com/CoatiSoftware/Sourcetrail/blob/master/DOCUMENTATION.md#graph-view),
выбор объектов и просмотр доказательств связей — на [Understand](https://docs.scitools.com/help/dependencies/browse-and-export-dependencies.html),
вложенные компоненты и авторские сценарии — на [Structurizr](https://docs.structurizr.com/dsl/cookbook/groups/),
а матрица зависимостей — на [DSM](https://www.ndepend.com/docs/dependency-structure-matrix-dsm/1000).
Это разные представления одной модели, а не отдельные базы.

«Документация» начинается с карточек разделов: руководство пользователя,
разработка приложения, создание шаблонов, расширения и API. Настройки проекта
могут добавлять собственные разделы. Внутри раздела слева находится дерево папок
и страниц, справа — статья, как в [Confluence](https://support.atlassian.com/confluence-cloud/docs/navigate-spaces/).
Поле «Папка» поддерживает вложенность через `/`. Поиск работает по страницам;
при переходе по ссылке статья открывается в своём разделе.
Можно создавать статьи, редактировать Markdown, просматривать его перед
сохранением, искать, читать историю и восстанавливать старую версию.
Тип статьи — учебный материал, инструкция, справочник или объяснение;
это отдельная классификация.
Статусы: draft/current/historical/archived. Длинные описания размещайте здесь,
а в архитектуре оставляйте короткое объяснение роли элемента или связи.
`entityRefs` статьи и `documentRefs` элементов обеспечивают переходы в обе стороны.
В блоке «Архитектура» статьи сначала показаны первые 20 связанных объектов
с названиями. Кнопка «Показать все» раскрывает оставшиеся ссылки; названия
загружаются порциями, а счётчик показывает ход загрузки. «Свернуть» возвращает
компактный список. Повторное раскрытие использует уже загруженные названия;
ошибку загрузки можно повторить отдельной кнопкой. Недоступные объекты отмечены
явно. Раскрытие и сворачивание не меняют текст или несохранённый черновик статьи.
Переход к статье обозначен явно; возврат к архитектуре сохраняет выбранное
представление, фильтры, камеру и ручное расположение узлов.

## Обновление и работа агента

`updateMode=manual` или `on-demand` запускает анализ по команде. `background`
включает периодический локальный scan, по умолчанию раз в 60 секунд. Можно задать
`intervalSeconds` от 30 до 86400. Обновление коалесцируется: для одного проекта
одновременно выполняется одна задача; всего работают два scan worker.
Парсинг неизменённых файлов повторно использует hash-кэш и версию адаптера/JDK.
Одинаковые факты не создают новую ревизию. Авторские описания, ссылки и раскладка
сохраняются при refresh. Удалённые типы остаются с отметкой removed, сохраняя ссылки.
При неполном анализе старые факты помечаются stale, а не считаются удалёнными.
Если исходники или политика изменились во время анализа, результат не применяется.

Codex получает `hub_knowledge` и инструкции в поставляемом навыке Project Hub.
Команда «заполни архитектуру и документацию проекта» запускает чтение policy,
локальный scan, описание важных элементов и создание/импорт нужных статей.
После обычной задачи агент обязан оценить влияние без отдельного запроса:

- изменения компонентов, наследования, зависимостей, точек входа и форматов:
  scan и обновление затронутых авторских описаний/сценариев и документации;
- изменения видимого поведения, сценариев пользователя или конфигурации:
  обновление документации, даже если структура кода прежняя;
- косметика и внутренние правки методов без такого влияния: no-impact с причиной.

`impact` возвращает затронутые IDs. С `record=true`, `task`, `stage` и `change.reason`
оценка сохраняется; нерешённая оценка видна в UI. После проверки/обновления
`change.knowledgeUpdated=true` отмечает её выполненной. Это утверждение агента,
не автоматическое доказательство семантики. Сбой Hub не блокирует изменение кода.
Фоновый scan обновляет факты, но не пишет человекочитаемые статьи за агента.

## Единый контракт

HTTP: `/api/v1/knowledge?project=<id>`. Чтения принимают `action` и query arguments;
JSON POST содержит `{"action":"changeset","args":{...}}`. MCP `hub_knowledge`
принимает те же action/args и связывает проект с проверенной сессией.

Действия: context, search, read, history, changeset, scan, job, import-preview,
import-read, import-apply, impact, restore, export. Крупные backup/restore/download выполняются
через HTTP/CLI. Это намеренное ограничение MCP с транспортом 16 KB на запрос
и 256 KB на ответ, а не попытка отправить всю базу в контекст агента.
MCP import-preview возвращает компактный список кандидатов и readArgs;
import-read читает markdown/diff по identifier, index, offset/limit (до 12000
символов). HTTP preview передаёт полный материал для редактора. MCP export
проверяет выбранный состав и возвращает число элементов и ссылку на download.
History ограничивает страницу и числом, и байтами; changedCount/changedMore
отмечают усечённый перечень IDs, immutable history сохраняется целиком.

У каждого элемента стабильный `id` и `kind=document|entity|relation|view`.
Changeset задаёт независимую числовую `expected` knowledge revision, уникальный
`key`, `reason`, `operations`, при работе агента — `task` и `stage`.
`validate_only=true` проверяет без записи. Ревизия плана Hub имеет другой контракт.
Связанные изменения применяются одной SQL-транзакцией. Конфликт не затирает данные;
повтор с тем же key и содержимым возвращает прежнюю ревизию.
Восстановление статьи создаёт новую версию и не откатывает код.

История хранит автора, причину, задачу/этап, изменённые IDs и `codeRevision`.
Scan записывает точный fingerprint охваченных исходников и доступные HEAD корней.
Авторская правка использует явно переданный code_revision либо последний scan
с отметкой основания; отсутствие привязки не подменяется текущим HEAD.
Для связанных с задачей изменений транзакция создаёт outbox. Сервер через обычный
API журнала публикует запись «Знания: версия …» с immutable evidence, безопасно
повторяет доставку; `publicationPending` показывает незавершённую доставку.
Проверки и Git checkpoints остаются отдельными событиями той же задачи/этапа.

Созданные статьи прикрепляются к задачам через `knowledge/document/<id>`;
`knowledge/revision/<n>/document/<id>` адресует существующую историческую версию.
MCP source read возвращает versionRef для согласованных страниц. При переносе
задачи применяется существующая provenance-модель `hub-source/<project>/...`.
Импортированная статья и историческая версия не требуют исходного файла.

## Импорт, экспорт и сохранность

Импорт принимает 1–50 Markdown/text файлов из зарегистрированных корней.
Preview копирует оригинальные байты и найденные локальные изображения в
immutable blob store и показывает create/duplicate/unchanged/review и diff.
Повторное изменение исходника не заменяет вручную отредактированную статью,
пока обновление не выбрано явно. Не найденные изображения, относительные ссылки
и includes отмечаются как неполный импорт; внешние ресурсы не скачиваются.
Оригиналы не перемещаются и не удаляются. Планы/отчёты импортируются черновиками:
их актуальность нужно проверить перед статусом current.

Текст, метаданные и immutable history находятся в существующей registry.sqlite3;
assets — в управляемом data home `projects/<id>/knowledge/blobs`. Это отдельные
таблицы существующего каталога, без замены журнала задач и создания новой базы.
Backup содержит согласованный снимок, политику, историю и все referenced blobs.
Restore разрешён в пустое хранилище зарегистрированного проекта, проверяет
хеши/историю/ссылки и не требует файлов репозитория.

«Экспорт ZIP» выгружает knowledge.json, Markdown, assets и manifest с hashes.
Это переносимое одностороннее зеркало: его можно сохранить в Git, оно не
синхронизируется обратно и не делает push. «Резервная копия» включает историю;
обычный экспорт её не заменяет.
Публичный экспорт принимает только явно `public-approved` самостоятельные статьи,
отклоняет внутренние связи, raw HTML, локальные ресурсы/includes и source metadata.
В него не входят внутренние IDs проекта/статей, история и закрытый индекс.
Публикация сайта — отдельная операция.

CLI: `python scripts/project_hub_knowledge.py --url http://127.0.0.1:8769
--project PROJECT --action context`. Для записи используйте `--args-file FILE.json`.
`--action download --output knowledge.zip` выгружает зеркало;
`--action backup --output backup.json` — полную копию.
Restore: action restore-backup, args file `{"backup":{...}}`.

## Проверка

Изолированные проверки находятся в test_knowledge_store.py, test_knowledge_http.py
и test_knowledge_ui.py. Они покрывают конкуренцию, перенос ссылок, imports/assets,
backup без repo, public privacy, partial/stale анализ, multi-root, очередь scan,
навигацию графа, дерево документации и сохранение черновиков. Полный project-local runner остаётся
обязательным для изменений общих серверных контрактов и плагина.
Методика изолированных замеров и ограничения локального сервера описаны в
[руководстве по производительности](../hub-performance-runtime.md).
