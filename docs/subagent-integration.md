# Подагенты и Project Hub

Цель интеграции — дать каждому исполнителю доступ к общей памяти, плану,
резервированиям и результатам других исполнителей под собственной идентичностью.
Дерево команды в портале показывает эти связи, но не заменяет координацию.

## Контракт идентичности

В совместимом desktop runtime подагент получает собственный `CODEX_THREAD_ID`.
`CODEX_SESSION_ID` остаётся идентификатором основного агента. Подагент читает
только `CODEX_THREAD_ID`, один раз вызывает `hub_context(session=...)` и проверяет
возвращённые `session` и `project`. После привязки session опускается.
Унаследованный startup-контекст родителя не идентифицирует подагента.
При отсутствии достоверного ID или `session_mismatch` запись прекращается;
выводы можно передать родителю штатными сообщениями Codex.

В `PreToolUse` используется другое представление той же идентичности:
`session_id` содержит корневую сессию, `agent_id` — фактического исполнителя.
HTTP-клиент сохраняет `agent_id`; сервер выбирает его **до** определения проекта,
регистрации события и проверки claims. Исходная сессия остаётся в
`origin_session_id` как происхождение события, а не владелец прав.
Отсутствие `agent_id` сохраняет обычный контракт корневых hooks.
Некорректный непустой actor не подменяется родителем.

Связь с непосредственным родителем читается из локального каталога Codex:
`source.subagent.thread_spawn.parent_thread_id`. Дополнительно читаются путь,
имя и роль агента. Это адаптер локального формата, не обещание стабильного API.
Циклические/некорректные связи не используются. Наблюдённая связь зарегистрированной
сессии сохраняется в `session_agents` и переживает недоступность каталога.
Родство не назначает проект, задачу или права на чужие ресурсы.

## Полезный цикл работы

1. Основной агент передаёт существующие task/stage, конкретное поручение и пути.
2. Исполнитель привязывает собственную сессию, читает `hub_plan` и релевантную
   `hub_memory`, чтобы использовать уже полученные результаты.
3. Исполнитель вызывает собственный `hub_begin` для файлов и общих ресурсов,
   например каталога сборки. Разные пути можно обрабатывать одновременно.
4. При уведомлении `resource_overlap` агент проверяет владельца и область
   пересечения. `hub_context(work=id)` даёт детали, а `hub_memory` находит
   сохранённый результат. Действительные пересечения согласуются средствами
   клиента. Старые записи `resource_busy` остаются частью истории.
5. `hub_report` сохраняет результат, checkpoint и ссылки. Только владелец может
   обновить или завершить работу. `done` освобождает её claims, `waiting` сохраняет.
6. Основной агент принимает результаты и проверяет интеграцию. Отчёт одного
   исполнителя не завершает всю задачу и не освобождает резервирования соседа.

`hub_context` возвращает компактные заголовки задач вместо всей истории этапов.
Полный план остаётся доступен через `hub_plan`. Раздел `team` содержит собственную
идентичность, родителя, соседей, текущие работы и недавние результаты с work/task/stage.
Выдача ограничена; `more` и прямые work-ссылки не дают молча принять срез за весь план.

## Завершение и границы защиты

Stop/Interrupt/SessionEnd не завершают работу автоматически и не передают claims.
Перед остановкой исполнитель сохраняет checkpoint и явно освобождает завершённую
работу. При аварии незавершённые резервирования остаются видимыми; отсутствие
сигнала не означает, что ресурс свободен. Возобновлённая собственная сессия может
продолжить работу по сохранённой revision.

Текущий набор обработчиков не подписывается отдельно на SubagentStart/SubagentStop.
Обнаружение в каталоге не доказывает активный запуск. Последнее событие, результат
работы и подтверждение подключения показываются отдельно; для устаревшего сигнала
нельзя утверждать, что подагент продолжает выполняться.

Claims описывают заявленные ресурсы и пересечения работ. Доступ к файлам
определяют штатные разрешения клиента и операционной системы; обработчики Hub
не запрещают правки и не дают разрешений. Сам обмен сообщениями между агентами
остаётся в инструментах клиента. Ошибка учёта не останавливает разрешённую работу.

## Проверки

`scripts/tests/test_subagent_integration.py` использует только временные каталоги,
проекты, сервер и data home. Проверяются права родителя/соседа, разные пути,
содержательные ошибки конфликтов, поиск результата другого исполнителя,
остановка родителя, сохранение связи после потери каталога и MCP identity.
Синтетические тесты транспорта не подменяют реальную desktop-приёмку.

## Разрешения клиента

Делегирование, доступ к MCP-инструментам и native файловые разрешения настраиваются клиентом независимо. Hub сохраняет identity, области работы и результаты. Он не меняет доверие к инструментам или настройки разрешений. Подтверждения, требуемые клиентом, остаются его собственной частью подключения.
