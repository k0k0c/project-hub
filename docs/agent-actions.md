# Действия агента и обзор проекта

## Запуск задачи в текущем приложении

Нажмите индикатор работы агента рядом со статусом задачи или этапа, чтобы открыть
окно запуска. Кнопка доступна на странице задачи, в списке задач и на карточках
обзора проекта. В окне можно выбрать приложение и его проект, создать новый чат
или продолжить связанный чат, а также добавить инструкцию. По умолчанию выбран
режим **Создать новый чат**. Список чатов появляется при выборе **Продолжить чат**.

Hub выбирает приложение создателя задачи по сохранённым сведениям о её происхождении.
Если определить его нельзя, единственное доступное приложение выбирается автоматически;
при нескольких вариантах выберите приложение сами. Ваш ручной выбор сохраняется при
обновлении состояния окна. Если у выбранного приложения есть несколько привязок к этому
проекту Hub, появляется отдельный выбор рабочего пространства. Проект Hub может
объединять несколько папок кода и проектов в приложениях; задача не всегда определяет
одну такую привязку. Известная однозначная привязка создателя выбирается по умолчанию.

Кнопка задачи запускает работу над всей задачей: агент читает актуальный план
и начинает или продолжает незавершённые этапы с учётом зависимостей и препятствий.
Завершённые и отменённые этапы пропускаются. Кнопка этапа запускает только этот этап.
Открытие окна само по себе не запускает работу; отправка происходит по кнопке
**Запустить**. Если все этапы завершены или отменены, запуск всей задачи недоступен,
но история запусков остаётся доступна во вкладке **Чаты** задачи.

Для текущего Codex используется отдельный
[экспериментальный адаптер](codex-desktop-control.md); приложение должно оставаться
запущенным. Во вкладке **Чаты** блок **Запуски из Hub** показывает последние запуски
задачи и её этапов: приём команды приложением, подтверждение получения агентом и
сохранённый результат с источниками и ссылкой на чат. «Запуск завершён» означает,
что закончился этот запуск, а не вся задача. Сводка результата — это отчёт,
переданный агентом в Hub; она не копирует последнее сообщение переписки. Работа
в связанном чате сама по себе не создаёт запись о запуске из Hub.

Прямой анализ через **Запросы к моделям** работает независимо от Codex и не создаёт
его чаты. Подробнее — [настройка сервиса модели](agent-analysis.md).

## Отдельный runtime через stdio

Ниже описан прежний экспериментальный исполнитель через самостоятельно запущенный
App Server. Его настройки и ограничения не относятся к управлению текущим Codex
через адаптер и не нужны для прямых запросов Hub к сервису модели.

Индикаторы агента, оценки задачи/этапа и кнопка обзора текущих задач открывают
один диалог. Область всегда указана явно: проект, задача или один этап. Проект
включает все незавершённые задачи, в том числе скрытые, будущие и эпики. Область
задачи включает все этапы кроме `done`, включая отменённые пункты с причиной;
зависимости и занятая другим чатом работа определяют порядок выполнения.

Запуск выполняется только по основной кнопке. Открытие страницы, наведение,
загрузка сводки и обновление статуса не запускают модель. Выбор нового чата
явный. Связанные native чаты без сохранённого собственного runtime показываются
недоступными; занятый или неизвестный чат не заменяется новым автоматически.
Экспериментальный stdio-адаптер включается существующей настройкой
`PROJECT_HUB_CODEX_ADAPTER=stdio`. Видимость его чата в Codex desktop и привязка
произвольного desktop-чата пока не подтверждены.
Для службы Windows можно явно добавить `-EnableCodexAdapter` в действие
`run-project-portal-service.ps1`; при новой установке автозапуска тот же параметр
принимает `install-project-portal-startup.ps1`. Параметр сохраняется в Планировщике
и действует после перезапуска. Установка не заменяет чужую конфигурацию службы.
Запрос исследования архитектуры содержит обязательную текущую ревизию знаний;
устаревший выбор отклоняется до запуска агента.

Windows-служба сначала ищет CLI в PATH, затем в versioned bin установленного
Codex (`LOCALAPPDATA/OpenAI/Codex/bin`). Это устраняет зависимость от PATH,
который приложение добавляет только своему процессу. Отсутствие CLI и сбой
запуска возвращают понятную ошибку, а не успешное подтверждение запроса.
Холст сразу показывает запуск агента и отмечает выбранный узел; затем
обновляет состояние по receipt actionId. Сервис сохраняет только категорию
текущего действия (работа, инструменты, ответ), без команд, переписки и полного
текста размышлений. Короткие публичные сводки `summaryTextDelta`, если модель их
предоставляет, показываются в общей центральной строке статуса: максимум 480
символов и обновление не чаще пяти секунд. Сводка хранится только в памяти
активного runtime; в квитанцию и базу она не попадает. Журнал содержит ссылку
на собственный native чат; видимость этого
чата в desktop приложении остаётся непроверенной.

Для архитектурных исследований проектные значения находятся в
«Настройки → Архитектура и код». Модель выбирается из native `model/list`;
чтение каталога не создаёт чат и не запускает генерацию. Значение «Codex по
умолчанию» не передаёт override; явная модель передаётся только в `thread/start`
нового исследовательского чата. Главный чат, авторизация и native разрешения
не меняются. В запросе агента доступна подробность `brief|standard|detailed`;
при отсутствии параметра используется проектный `descriptionDetail`.
Детальный запрос сохраняет описание выбранного объекта (до 12000 символов),
а не создаёт отдельную статью. Старые файлы настроек и их журнал дополняются
значениями по умолчанию при чтении, без изменения ревизии или истории.

Новый HTTP запрос запуска содержит `target`, `task`/`stage` по области,
`mode=plan|default`, `intent` или null, `expected` и стабильный `actionId`.
Сервер проверяет текущую ревизию, фиксирует полный набор ID в существующем CAS
и сохраняет квитанцию до native мутации. Точная повторная отправка того же ID
не создаёт второй ход. Неизвестный результат сохраняет исходный ID и требует
сверки квитанции. Продолжение подтверждённого сохранённого runtime получает
delta прежней фиксированной области: изменённые строки/этапы, вышедшие из
области ID и адресные offsets. Полная новая область остаётся в immutable
scopeRef; неполное покрытие delta требует дочитать нужные страницы. Выход из
области сам по себе не доказывает завершение. Native `collaborationMode` сохраняет настроенные model и
reasoning effort; Plan не имитируется текстом запроса. Неизвестные настройки
модели не подменяются предположением. Старый HTTP формат сохранён только для
совместимости прежнего экспериментального адаптера.

`hub_begin` отделён от создания задачи/этапа. Работа имеет фазу `planning`,
`research`, `implementation`, `review` или `testing` и один либо несколько
существующих этапов через `stages`. Одна работа сохраняет один исходный Git
boundary; все её этапы остаются в immutable coverage при одном коммите.
Без этапа допустимо только начальное планирование задачи, у которой этапов ещё
нет. `hub_report(stage=...)` выбирает этап для изменения его статуса; при
нескольких связях неоднозначное завершение отклоняется. `status=waiting`
с `waiting_kind=user_confirmation|external_dependency` отличает ожидание от
работы. Создание новой стадии не служит способом регистрации неожиданного
исследования внутри реализации.

Сервисные цели обзора: `review`, `next-step`, `relevance`, `estimate`,
`closure-review`. Это чтение/исследование с собственным work и read claims на
существующей задаче из области. Начало такого work не переводит план в active.
Сводка передаёт 8–12 KiB UTF-8 страницами, сохраняет все ID и ссылки на полные
детали. `hub_review(action=summary,actionId,scopeRef,offset)` читает страницы
собственной фиксированной области; обычная summary с expected читает текущую
ревизию. Один обзор не требует отдельного запуска модели для каждой задачи.

`hub_review(action=propose)` требует собственного action/work, текущей ревизии,
семантического `expectedState` каждой цели и immutable доказательств. Предложения
`current`, `done`, `superseded`, `duplicate`, `clarify` сохраняются как артефакт
авторства и отображаются пользователю. `done` требует доказательства каждого
критерия приёмки и оставшегося требования. Предложение `current` для всей задачи
может содержать `priority`: существующий уровень или null для снятия приоритета.
Приоритет показывается до выбора, меняется только при apply и блокируется
открытой write работой. Возраст и похожее название сами по
себе не доказывают завершение или дублирование.

Только кнопка «Применить выбранные изменения» отправляет local same-origin
`/api/v1/review-apply` с ref, выбранными ID и текущей ревизией. MCP не содержит
операции apply. Открытая write работа препятствует закрытию. Замена/дубликат
отменяет исходный пункт с причиной, сохраняет ссылки и переносит все
неразрешённые требования и доказательства в указанный существующий этап;
новый этап автоматически не создаётся. Назначение переноса показано до apply
и тоже проверяется по expectedState. При частичном результате сервер возвращает
applied/remaining и свежую ревизию; успешные события не повторяются. Изменённую
после частичного переноса цель следует заново рассмотреть.

Только явный intent `estimate` разрешает `hub_review(action=estimate)` обновить
метаданные оценки. Статус, объём и иерархия при этом не меняются. Диапазоны
описывают оставшееся активное время анализа, редактирования, интеграции и
необходимых проверок; ожидание пользователя, очередь и паузы исключены.
Неизвестное время оставляют без обеих часовых границ, а не заменяют нулём.
Готовность определяется критериями приёмки. Сводка складывает уникальные
группы работы последовательно для одного агента, исключает двойное сложение
эпиков/детей и явных дубликатов, показывает неизвестное покрытие. Калибровка по
фактическим наблюдениям пока не заявлена.

Ответ на native `item/tool/requestUserInput` коррелируется с action, thread,
turn и request ID. Сохраняются ограниченные вопросы, ответы передаются только
native процессу. Secret вопросы и запросы command approval здесь не
обрабатываются. Потерянное подтверждение ответа не разрешает слепую повторную
отправку. Native разрешения, sandbox и настройки модели остаются независимыми
от bookkeeping Hub.


Architecture `structure-map` actions require a saved `viewType=research`
snapshot and an explicit scope `{kind: canvas|result, viewId, resultId?}`.
The view ID must equal the research object ID; result scopes include an existing,
current result ID whose participants contain the snapshot. The server checks
all result pages, revision CAS and the native project root. The handoff contains
only the view reference and counts. The agent publishes a separate research
view with local `presentationGroups`, preserving canonical ownership. A named
subsystem `decompose` action applies to its complete direct/child composition;
it is unavailable for a class. Scope submission follows the same explicit UI
launch, progress and receipt contract as other agent research actions.
