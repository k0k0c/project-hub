# Project Hub local portal

Локальный постоянный портал проекта. Первая версия: задачи, этапы, зависимости, результаты проверок и история с живым обновлением. Архитектура/код, документация и действия — видимые заготовки будущих разделов. YouTrack не используется. Старые документы пока не импортируются автоматически.

## Запуск

Из корня проекта, с Python 3.10+ на PATH:

```powershell
powershell -File scripts/start-project-portal.ps1
```

Откроется `http://127.0.0.1:8769`. Повторный запуск использует уже работающий сервер этого checkout. `-NoBrowser` запускает только сервер; `-Port 8770` позволяет выбрать другой порт. Сервер привязан только к loopback и не зависит от Java-приложения. Закрытие вкладки или Codex не удаляет данные.

### Независимый запуск Windows

Установка пользовательского автозапуска и ярлыка на рабочем столе:

```powershell
powershell -NoProfile -File scripts/install-project-portal-startup.ps1
```

Установщик настраивает локальный запуск по выбранным параметрам оператора.
Он не требует фоновой службы, не включает удалённый доступ и не меняет доверие
Codex автоматически. Откройте показанный локальный адрес после запуска.

Правый клик: открыть хаб, запустить/остановить/перезапустить сервер, переключить запуск сервера при входе Windows, открыть папку журналов, скопировать адрес, открыть Планировщик, убрать значок. Двойной клик открывает браузер. Выход из трея не останавливает сервер. Переключатель автозапуска меняет trigger задания, поэтому ручной запуск остаётся доступен. Сам значок продолжает запускаться при входе, даже если автозапуск сервера отключён. Windows может первоначально поместить значок в скрытую область рядом с часами; пользователь может закрепить его в видимой области.

Реализация: `scripts/project-portal-tray.ps1`, штатные Windows Forms/.NET без стороннего Python GUI-пакета. Проверка `powershell -NoProfile -STA -File scripts/project-portal-tray.ps1 -SmokeTest` действительно выполняет команды меню остановки/запуска/перезапуска и переключения автозапуска, восстанавливает исходный trigger и оставляет сервер запущенным. Результат — `.local/project-portal/tray-smoke.json`. Это проверка с кратковременной остановкой локального сервера; не запускать её во время зависимых проверок.

Это пользовательский фоновый процесс, а не системная служба: до входа пользователя, после выхода из Windows или во время сна компьютера доступность не обещается. Для работы до входа потребуется отдельная служба с настройкой учётной записи и доступа к данным. Текущий вариант предназначен для локального хаба на рабочем компьютере.

Автоматический запуск — отдельный выбор оператора. Конфигурация привязана к
выбранной папке установки и интерпретатору Python; после их переноса повторите
настройку. Удалённый сетевой доступ не включён.

Без установленного задания стартовый скрипт сохраняет прежний режим фонового запуска из текущего процесса; этот запасной режим не гарантирует независимость от завершения сеанса запускающего приложения.

Хаб состоит из Python HTTP-сервера, статического веб-интерфейса и хранилища
данных в настроенном data home. Плагин Codex — клиент/адаптер к этим данным,
а не сам веб-сервер. Просмотр хаба не требует запущенной модели. MCP и hooks
могут записывать координацию, когда веб-сервер недоступен.

Для работы в текущем терминале: `python scripts/project_portal.py serve`. Остановка — Ctrl+C. Данные сервера/PID/логи лежат в `.local/project-portal/` и не коммитятся.

## Источник данных

- Настроенный data home содержит начальный срез проекта, журналы и исходные источники. Эти файлы являются данными пользователя, а не частью исходного кода.
- Оба файла — часть проекта и могут храниться в Git. Не переписывать историю при завершении задачи; добавлять новую задачу или новое событие. Во время разработки baseline первой версии может уточняться; после приёмки изменения идут через события.
- Запись: OS-lock между процессами, полная временная версия, flush/fsync и atomic replace. Неудачная запись не заменяет предыдущий полный журнал. Непонятная версия или повреждённый журнал отклоняются, а не обнуляются.

Это файловое хранилище задач и результатов проверок. Запись и восстановление линейны по числу событий; для многолетнего журнала можно добавить checkpoints/сегменты. Новая координация сессий и резервирований использует отдельную общую SQLite (см. ниже); старый журнал сохраняется для совместимости.

## Как агент обновляет прогресс

### Восстановление аварии сервера

Запускатель `scripts/run-project-portal-service.ps1` сам наблюдает завершение дочернего Python-процесса: ненулевой код вызывает до трёх повторных запусков с задержкой 5 секунд. После пяти минут стабильной работы счётчик повторов сбрасывается при следующем завершении. После исчерпания попыток запускатель выходит с кодом 1; дальнейшие попытки зависят от задания Windows. Код 0 завершает запускатель штатно. Журнал восстановления: `.local/project-portal/recovery.log`.

Правила для новых чатов в этом checkout находятся в корневом `AGENTS.md`.
Правила в корне репозитория дополняют инструкцию агента. Плагин маршрутизирует
зарегистрированные Git worktree в общую координацию по git common directory;
не предполагайте, что произвольный checkout зарегистрирован.

При начале/завершении существенного шага, проверке, находке или изменении плана публиковать событие. Не публиковать внутренние рассуждения, секреты или каждую строку лога. Журналы запусков прикладывать ссылками. При продолжении после перерыва сначала прочитать `state` и актуальную точку продолжения.

```powershell
python scripts/project_portal.py state
python scripts/project_portal.py record --file path/to/event.json
```

`record` без `--file` читает JSON из stdin. Пример:

```json
{
  "id": "unique-stable-retry-id",
  "taskId": "architecture-refactor",
  "stageId": "runtime",
  "kind": "work.started",
  "title": "Проверка жизненного цикла подписок",
  "detail": "Закрытый контейнер, повторная активация и undo."
}
```

Повторное событие с тем же ID и содержимым возвращает первоначальную запись. Другое содержимое с тем же ID отклоняется. Дата присваивается при записи; исходную дату старого результата указывать в описании/доказательстве, а не подменять время события.

События: `task.created`, `task.updated`, `stage.updated`, `work.started`, `work.completed`, `check.started`, `check.passed`, `check.failed`, `finding`, `decision`, `note`. Изменения task/stage передаются полем `patch`. Например, `stage.updated` с `patch: {"status":"done","done":["Проверено..."],"remaining":[]}`. Новая задача — `task.created` с новым taskId и patch title/status/stages. Все старые задачи остаются в проекте. Статусы: planned, active, queued, blocked, done, cancelled. Не ставить done, пока критерии завершения не выполнены.

`work.completed` может содержать `workId` — ID соответствующего work.started: поздний результат тогда не завершит более новую работу. Ссылки задаются `evidence: [{"label":"Результат","path":"target/test.log"}]`; только относительные пути внутри checkout. Браузер читает только зарегистрированные источники, размер до 4 MB. После Maven clean исчезнувший лог показывается как недоступный; важные итоговые доказательства следует сохранять в постоянных файлах проекта.

## Проверки с автоматическим результатом

```powershell
python scripts/project_portal.py run --task project-hub --stage verification --title "Portal contracts" --log target/project-portal-tests.log -- python -m unittest discover -s scripts/tests -p test_project_portal.py -v
```

CLI фиксирует начало, запускает процесс, сохраняет stdout/stderr и реальный код возврата, затем пишет check.passed/failed. Browser не запускает команды. Если процесс/машина аварийно завершились до записи результата, незавершённая проверка остаётся в истории без выдуманного успеха; следующий агент должен опубликовать уточнение.

## Живое обновление

Read-only HTTP: `/api/state`, `/api/history` (task/before/limit), `/api/evidence`, `/api/events` (SSE), `/api/health`. Поток отправляет новую ревизию; браузер получает целостное текущее состояние. При переподключении сервер сразу отправляет актуальную ревизию, а полная история остаётся доступной отдельно. Выбор задачи, раздела и этапа не теряется при обновлении. Обновление обычно занимает меньше секунды после успешной записи события; это не жёсткая гарантия задержки ОС/браузера.

«Связь» означает соединение с сервером портала, а не подтверждение работы агента. Время последнего события показано отдельно. Поле текущей работы — последнее явно начатое и ещё не завершённое действие. Пауза в событиях не интерпретируется как остановка агента.

## Границы расширения

Текущие сущности: Project, Task, Stage, Event, Evidence, Run. Стабильные ID предназначены для связей с будущими Document, System, Class, Decision и Action. Схема версионирована. Старые Documents/Roadmaps позже импортируются с происхождением, исходной датой и актуальностью; это отдельный тип исторических источников. Будущие действия будут иметь собственный реестр, параметры, разрешения и результат выполнения. В этой версии нет исполнения команд из браузера, удалённого доступа, новой консоли или интеграции с чатом.

Проверки: стандартный `unittest` в `scripts/tests/test_project_portal.py` и `test_project_hub_plugin.py`, проверка JS через `node --check tools/project-portal/web/app.js`, визуальная приёмка в браузере. Runtime использует стандартную библиотеку Python, без CDN. Валидатор пакета Codex отдельно требует PyYAML.

## Плагин и общая координация

Канонический исходник плагина находится в `tools/project-portal/plugins/project-hub`;
установка и обновление выполняются через `python scripts/install_project_hub_plugin.py`.
Этот скрипт сохраняет остальные личные плагины и не изменяет доверие hooks.

Пять готовых MCP-инструментов: `hub_context` (сводка, дельта или поиск), `hub_task` (создание задачи), `hub_begin` (шаг и резервирование), `hub_report` (результат/checkpoint/завершение), `hub_wait` (ограниченное ожидание). Идентификаторы и технические события создаёт инфраструктура. В резервном CLI `python tools/project-portal/plugins/project-hub/scripts/hub_plugin.py --help` доступны context/begin/report/doctor/register.

Общая база: `~/.codex/project-hub/coordination.sqlite3`. Резервирование действует до явного завершения владельцем; закрытие или молчание задачи не освобождает файлы. Поддерживаемые структурированные правки проверяются hook; произвольная запись через shell и неподключённые задачи пока не защищены. В портале `/api/coordination` и «Чаты и согласование» показывают подключённые сессии и их независимые шаги.
